## הבעיה שהייתה צריכה פתרון: אפס סנכרון

לפני העבודה הזו לא היה בקוד **שום** מנוי `postgres_changes` — אפס. כל מסך קרא
את הנתונים פעם אחת, כשנטען. זה בסדר לנייד שנפתח ונסגר, אבל שגוי לחלוטין למסך
שנשאר על אותו דף במשך שבועות: גבאי שמשנה זמן תפילה לעולם לא היה מגיע לקיר.

### הפתרון — `src/community/lib/realtime.ts`

`useRealtimeSync()` נרשם לפיד השינויים של Postgres ומבקש מ-React Query לטעון
מחדש רק את הרשימה שהשתנתה.

שלוש שכבות הגנה, כי אין מי שילחץ "רענן":

1. **Realtime** — שינוי מגיע למסך תוך שנייה.
2. **טעינה תקופתית** — כל 5 דקות, ללא תלות בסוקט. אירוע שהוחמץ היה נשאר
   על המסך עד ריענון הדף, שעל קיר עלול לא לקרות לעולם.
3. **התחברות מחדש** — backoff מדורג עד 30 שניות, ואיפוס מיידי כשהרשת חוזרת
   (`online`). כל התחברות מחדש טוענת הכול, כי ייתכן שהוחמצו שינויים.

#### איך זה אומת

`scripts/verify-realtime.mjs` נרשם לשינויים, מבצע כתיבה, ומוודא שהאירוע
הגיע. הרצה חוזרת:

```bash
node scripts/verify-realtime.mjs
```

**למה כלי כזה נחוץ:** מנוי בלבד לא מוכיח דבר. Supabase Realtime מאשר
binding לכל שם טבלה — בדקתי עם בקרה, וגם `this_table_does_not_exist_xyz`
קיבלה "אישור". ניסיון קודם שהסתמך על סטטוס המנוי דיווח 8/8 הצלחה והיה
חסר ערך לחלוטין; הוא נמחק ולא נכנס לרפו.

הכתיבה היא no-op מכוון — אותו ערך נכתב בחזרה לאותה עמודה, כך שהנתונים
לא משתנים אבל Postgres עדיין מפיק UPDATE.

בנוסף אומת שהלוח עצמו מגיב: עם הלוח פתוח, כתיבה חיצונית גרמה לו לטעון
מחדש את `settings` לבד (2 → 3 בקשות), בלי ריענון דף ובלי נגיעה.

RLS לא מושפע: realtime מחיל את אותן מדיניות שורה, כך שמנוי מקבל בדיוק את
השורות שמותר לו לקרוא.

שלוש שקופיות מתחלפות אוטומטית, 20 שניות כל אחת:

1. **זמני תפילות** — מניינים של היום, עם סימון בולט של **המניין הבא**, לצד

(`resolveDay`, `zmanimFor`) — לא שוכפלה, כדי שלא ייווצר הבדל בין המסך לנייד.

### הערה על `scripts/tv-cap.mjs`

ה-CLI של Capacitor מחפש `capacitor.config.ts` בשם קשיח ואין לו דגל `--config`
(נבדק ב-`@capacitor/cli/dist/config.js`). לכן הסקריפט מחליף את קובץ התצורה
לזמן הפקודה בלבד.

ההחלפה היא החלק המסוכן: אילו הייתה נשארת חצי-מיושמת, הבילד הבא של הנייד היה
יוצר APK עם ה-appId של הטלוויזיה בשקט. לכן השחזור רץ מתוך `finally` וגם
ממטפלי אותות, והמקור נשמר בזיכרון ולא בקובץ גיבוי שעלול להישאר ולהיראות
כמו התצורה האמיתית.

### ארבעה באגים שנמצאו רק על המכשיר — ותוקנו

1. **מסגרת כתומה סביב כל המסך.** טבעת הפוקוס של ה-WebView מופיעה אחרי לחיצה על השלט.

   בדיוק מה שנצרב בפאנל. תוקן ב-CSS וגם ב-`setDefaultFocusHighlightEnabled(false)`.
2. **שיעורים לא לפי שעה:** 16:15, 08:45, 14:15, 15:15 (לפי `sort_order` של האתר).
   עכשיו ממוינים לפי השעה שבטקסט.
3. **ההפעלה האוטומטית לא עבדה, ודיווחה שכן.** ה-receiver הופעל ורשם "restarted",
   אבל אנדרואיד 14 חסם את פתיחת המסך **בשקט** (`Background activity launch blocked ...
   BAL_BLOCK`), בלי להחזיר שגיאה לאפליקציה. הפתרון הרשמי הוא ההרשאה "הצגה מעל אפליקציות

4. **`favicon.ico` → 404 בכל טעינה.** השרת המקומי של Capacitor לא מגיש `.ico` במכשיר
   (PNG ו-HTML מאותה תיקייה עובדים). ללוח אין לשונית דפדפן, אז הוגדר אייקון ריק.

## שליטה מלאה בלוח מהמחשב — `scripts/tv-control.mjs`

שני ערוצים, כי הם מגיעים לדברים שונים:

```
   המחשב                                    קופסת ה-TV
 ┌─────────────┐   ADB (adb shell)      ┌──────────────────────────────┐
 │             │ ─────────────────────► │ המכשיר: התקנה, הפעלה, מקשי   │
 │ tv-control  │                        │ שלט, צילום מסך, לוגים        │
 │   .mjs      │   CDP (DevTools)       │  ┌────────────────────────┐  │
 │             │ ─── adb forward ─────► │  │ בתוך ה-WebView: DOM,    │  │
 └─────────────┘   tcp:9222             │  │ JS, קונסול, רשת         │  │
                                        │  └────────────────────────┘  │
                                        └──────────────────────────────┘
```

`uiautomator` לא רואה שום דבר בתוך ה-WebView. זה נבדק על המכשיר ויצא ריק. לכן התוכן
נקרא דרך Chrome DevTools Protocol, כמו ש-`chrome://inspect` עושה.

```bash
npm run tv -- status            # מכשיר, אפליקציה, שקופית נוכחית, מצב סנכרון, אוטו-הפעלה
npm run tv -- text              # כל הטקסט שעל המסך
npm run tv -- eval "<js>"       # הרצת JavaScript בתוך הלוח
npm run tv -- console 30        # קונסול ושגיאות, 30 שניות
npm run tv -- network 30        # כל בקשות הרשת, 30 שניות
npm run tv -- shot tv.png       # צילום מסך מלא
npm run tv -- key down 3        # מקשי שלט: up/down/left/right/ok/back/home/menu
npm run tv -- reload | restart | install | autostart
```

**התחברות:** בטלוויזיה, הגדרות → אפשרויות מפתח → **ניפוי באגים אלחוטי**, ואז
`adb connect <ip>:<port>` עם הפורט שמוצג שם. **הפורט משתנה אחרי כל אתחול של הטלוויזיה.**

**אבטחה:** הערוץ לתוך ה-WebView (`webContentsDebuggingEnabled` ב-`capacitor.config.tv.ts`)
נגיש **רק** דרך חיבור ADB מאושר. Chromium מקבל חיבור רק מה-UID של ה-shell או של root.
מי שיש לו ADB יכול ממילא לשלוט במכשיר כולו, אז ההגדרה לא מרחיבה את הסיכון. **המתג האמיתי
לייצור הוא לכבות "ניפוי באגים אלחוטי" בטלוויזיה**, מה שסוגר את שני הערוצים. בנייה עם
`TV_WEBVIEW_DEBUG=0` משמיטה את הערוץ מה-APK.

**למה לא שרת MCP מוכן:** נבדקו mobile-mcp, android-mcp-server, scrcpy-mcp, mcp-adb ועוד.
כולם רואים רק את עץ הנגישות, **ואף אחד לא רואה בתוך WebView**. `chrome-devtools-mcp`
של Google יכול להתחבר ל-`localhost:9222` אחרי `adb forward`, אבל התמיכה שלו ב-WebView לא
מאומתת, ו-Puppeteer שעליו הוא בנוי נתקע מול אנדרואיד בחלק מהפקודות.

## הפעלה אוטומטית אחרי הפסקת חשמל

`BootReceiver.java` מפעיל את הלוח כשהטלוויזיה נדלקת.

מכשירי אנדרואיד TV לא עקביים לגבי איזה שידור אתחול הם שולחים, ולכן ה-receiver
מאזין לארבעה: `BOOT_COMPLETED`, `LOCKED_BOOT_COMPLETED`, `QUICKBOOT_POWERON`
ו-`com.htc...QUICKBOOT_POWERON`. כפילויות לא מזיקות — `MainActivity` היא
`singleTask`, כך ששידור שני מביא את המופע הקיים לחזית במקום ליצור עוד אחד.

> ⚠️ **זה best effort, ותלוי מכשיר.** אנדרואיד מגביל הפעלת activity מהרקע,
> וחלק מהמכשירים פשוט מסרבים. אם הלוח לא חוזר מעצמו — חפש בהגדרות הטלוויזיה
> אפשרות "הפעלה אוטומטית" / "Auto start" עבור האפליקציה. אי אפשר לעקוף את
> זה מהקוד. כישלון נתפס ונרשם ללוג במקום לקרוס, כדי שהמערכת לא תסמן את
> האפליקציה כבעייתית בכל אתחול.

### צימוד מסך
בטלוויזיה חדשה מופיע בפינה **קוד בן 6 ספרות**, והלוח ממשיך לפעול. מזינים את הקוד בטאב
"מסכים ושליטה" ונותנים שם. המסך מציג מיד את שמו בגדול כאישור. הקוד מבטיח שרק מסך
שעומד מולכם יתחבר. לטלוויזיה אין חשבון משתמש: היא מזדהה בסוד אקראי שנוצר עליה, ורק
גיבוב שלו נשמר בשרת.

### שיקוף חי ושלט רחוק
כל מסך מופיע עם **תמונה של מה שהוא מציג עכשיו**. זה לא וידאו: הטלוויזיה מדווחת באיזו
שקופית היא נמצאת, והאתר מצייר את השקופית באותו רכיב בדיוק. השיקוף מתעדכן תוך כשנייה
וכמעט לא צורך רשת. מהכרטיס אפשר: קודם/עצירה/הבא, לחיצה על שקופית כדי לעבור אליה,
ערכת נושא למסך הזה, **הודעה על המסך** (למשל "מנחה מתאחרת ב-10 דקות"), זיהוי,
טעינה מחדש, ו**צילום מסך אמיתי** (כ-36KB, תוך כ-2 שניות).

### מסגרות — צורת הפינה בשליטת המנהל

בלשונית העיצוב, מתחת לבורר הסגנון, יש **מסגרות**: בוחרים את צורת הפינה של כל
הלוחות — לפי הסגנון / מעוגל / רך (squircle) / קטום / מגורע / מדורג — ובנוסף שני
מחוונים נפרדים, **עיגול למעלה** ו**עיגול למטה** (0–12 יחידות `--u`), כל אחד עם
"לפי הסגנון" לחזרה לברירת המחדל.

- חל על כל הלוחות, בכל הסגנונות, בכל הפריסות ובכל המסכים (טלוויזיה, לפטופ, נייד).
- כשקובעים עיגול, הצורה של הסגנון (כיפה, קשת, קצה מסולסל) מוחלפת בפינה שנבחרה —
  `clip-path` חותך את הפינה לפני שרדיוס יכול לעגל אותה, ו-`border-image` מתעלם
  מרדיוס. החומרים והצבעים של הסגנון נשארים.
- הצורות הלא־עגולות משתמשות ב-`corner-shape` של CSS (נתמך ב-WebView של הקופסה,
  Chromium 152, ובכרום). בדפדפן בלי תמיכה נשאר העיגול בלבד — לא נשבר כלום.
- הערך נשמר ב-`config.frame` ומנורמל בטעינה: צורה לא מוכרת חוזרת ל"לפי הסגנון",
  ורדיוס נחתך ל-0–12.

## עריכה ישירה בלוח (click-to-edit) — 2026-09-18, Claude

**איך:** ניהול ← לוח תצוגה ← עיצוב ← **"עריכה ישירה בלוח"**. כל טקסט/אזור בלוח מסומן במסגרת מקווקוות; לחיצה עליו (בכל מכשיר בסטודיו: טלוויזיה, מחשב, לפטופ, טאבלט, טלפון או "כל המסכים") פותחת טופס עריכה. הכל נכנס לטיוטה (ביטול/חזרה, "ביטול שינויים") ומגיע למסכים רק ב"שמור ושדר".

**השיטה (כמו Sanity / TinaCMS):** כל רכיב נושא `data-edit="<מפתח>"` שמצביע על מקור הנתון; העריכה נעשית בשדה טופס אמיתי ולא בהקלדה על הטקסט המוצג (contentEditable נלחם ב-React על ה-DOM, מאבד סמן ו-undo). `data-edit` מופיע רק במצב עריכה — בטלוויזיה אין אותו (נבדק: 0 אלמנטים).

| מה | איפה נשמר | משפיע על |
|---|---|---|

המנגנון מכובה, פעם אחת, ומדווח. הלוח מאבד נוחות קטנה אחת וממשיך לעבוד. כרגע
ההקטנה האוטומטית של הטקסט עוברת דרכו (40 ריצות ב-5 שניות; החלפת שקופית עולה
בודדות). כרטיס שנכבה נשאר בגודל שאליו הספיק להגיע.

**שמירה על ה-thread הראשי** עצמו, למקרה שבורח משהו שאף מפסק לא עוטף. הדפדפן
מדווח על כל משימה שחוסמת אותו מעל 50ms; כששתי חלונות של עשר שניות ברצף היו
חסומים ברובם, זה לא רגע עמוס — זו לולאה. זה מדווח, והלוח טוען את עצמו מחדש,
לכל היותר פעם בשעה (לוח שמרענן את עצמו במעגל גרוע מלוח איטי).

שניהם מדווחים דרך אותו חיבור שהלוח כבר מדווח בו — כך שבאתר המנהל, ב"לוח
תצוגה ← יומן", מופיעה שורה בשם **"הגנה עצמית"**. מסך ששמר על עצמו אומר את זה,
במקום להיכשל בשקט.

נבדק: 13 בדיקות יחידה (`src/tv/watchdog.test.ts`) על המפסק, על חלון הזמן
המתגלגל, על סף הזיהוי ועל מגבלת הרענון; ובדפדפן אמיתי מול ה-bundle הבנוי של
הטלוויזיה — לולאה שתופסת את ה-thread הראשי זוהתה כ-100%, דווחה, והלוח נטען
מחדש פעם אחת וחזר תקין.

## תצוגות: לוח אחד, שלושה מסכים (2026-09-22, Claude)

עד עכשיו כל מה שהעורך החי עושה — הניסוח, מה נמצא על הלוח, הצבעים, הפריסה —
היה הגדרה אחת משותפת לכל מסך. לרובו זה נכון ולחלקו לא: הקיר בבית הכנסת הוא
טלוויזיה 1920×1080 שרואים מעשרה מטר, ואותו לוח בנייד בכיס הוא בעיה אחרת.
כותרת שנקראת יפה על פני אולם ארוכה מדי לנייד; לוח ששייך לקיר יכול להיות רעש
במחשב.

הטאב נקרא עכשיו **תצוגות**, ובראשו בורר: **כל התצוגות · אנדרואיד TV · מחשב ·
מובייל**. זו השאלה שעונים עליה פעם אחת כשמתיישבים — "אני מתקן עכשיו את
הנייד" — ולא היקף שמוצמד לכל פקד בנפרד. כל מה שמתחתיו מתכוון למה שכתוב בו,
והתצוגה המקדימה היא של אותו מסך.

**"כל התצוגות" היא ברירת המחדל וברוב המקרים הנכונה.** לוח הוא לוח אחד, והקיר,
המחשב והנייד אמורים בדרך כלל להגיד אותו דבר. רק מה שבאמת חייב להיות שונה שווה
להחזיק בשלושה מקומות. נקודה על טאב מסמנת שלמסך הזה כבר יש הגדרות משלו, כדי
שלוח שחולק על עצמו בשקט לא יוכל להסתתר.

### איך זה בנוי

לוח הוא בסיס משותף, ולכל סוג מסך שכבה (overlay) של מה שהוא עושה אחרת. שכבה
ריקה — וזו השכבה של כל לוח עד שמישהו משנה משהו — פירושה "כמו בכל מקום", ולכן
שום דבר לא צריך להיות מוגדר שלוש פעמים, ועריכה שאמורה לחול על הכל נשארת עריכה
אחת.

`configForDevice(config, device)` מחזיר `TvConfig` רגיל, וזו הנקודה: הלוח,
הערכות, הסגנונות והתצוגה המקדימה ממשיכים לא לדעת ששלוש תצוגות קיימות.

שני כללי מיזוג, וההבדל ביניהם חשוב:

- **מה שממופתח לפי אלמנט** — הניסוח, הסגנון לכל אלמנט, דריסות הצבע — מתמזג
  מפתח-מפתח. "כותרת קצרה יותר בנייד" משנה את אותה כותרת ומשאיר את השאר עוקב
  אחרי הלוח.
- **כל השאר מחליף במלואו**, כולל הרשימה של מה מוסתר. רשימה לא יכולה להתמזג: אם
  הלוח מסתיר לוח והמסך הזה רוצה אותו בחזרה, שום איחוד של שתי רשימות לא יכול
  להגיד את זה.

`editForDevice(config, device, fn)` מריץ עריכה רגילה על הלוח כפי שהמסך רואה
אותו, ושומר את מה שיצא שונה כשכבה של אותו מסך. הפקדים בעורך כולם בצורה
`(config) => config` ואף אחד מהם לא יודע שמסכים קיימים — ולכן פקד שיתווסף בשנה
הבאה יהיה ניתן להיקוף בלי שאיש יזכור לדאוג לזה.

**שלוש מחלקות ולא חמש.** התצוגה המקדימה מציעה גם טאבלט וגם לפטופ, כי לראות את
הלוח בגדלים האלה שימושי, אבל לבקש מגבאי לתחזק חמישה ניסוחים זה לא: לפטופ הוא
מחשב וטאבלט מחזיקים כמו נייד.

### בורר אחד, לא שניים (2026-09-22)

הגרסה הראשונה הייתה עם שני בוררים: אחד לתצוגה המקדימה ואחד להיקף העריכה.
בדיקה של איך כלים מקצועיים פותרים את זה ([Webflow](https://help.webflow.com/hc/en-us/articles/33961300305811-Breakpoints-overview),
[Elementor](https://elementor.com/help/mobile-editing/)) מראה שזו בדיוק הטעות
שמייצרת את התלונה הנפוצה ביותר על כלים מהסוג הזה: משנים משהו, לא קורה כלום,
וזה תפס על מסך אחר. בפורום של Webflow זה מנוסח כך — משתמש ששינה במובייל וגילה
שזה השפיע גם על דסקטופ.

אז יש בורר אחד: רצועת המכשירים מעל התצוגה המקדימה. בחירת מכשיר שם היא גם
בחירת מה שנערך, ומתחתיה שורה שאומרת במילים מה זה אומר כרגע. כשעורכים תצוגה
אחת השורה נצבעת ולא ניתן לפספס אותה.

**הבחירה לא נשמרת בין ביקורים** — כל כניסה מתחילה ב"כל המסכים". זו כל הבטיחות
של בורר אחד: אילו הבחירה נשמרה, מנהל שהסתכל בפעם שעברה על הנייד היה חוזר
שבוע אחרי, משנה כותרת, ומשנה אותה בנייד בלבד בלי שאיש אמר לו. כך העריכה
הרשלנית היא הבלתי-מזיקה.

**"כל המסכים" מראה לוח אחד, לא חמישה בולים.** ההשוואה היא כפתור — וכשלוחצים
עליה כל תצוגה מוצגת עם הלוח שלה, זו לצד זו, וההבדלים נראים במבט אחד. זה
הפתרון ש-Webflow הוסיפו ב-2025 לאותה בעיה בדיוק.

**החזרה אחורה היא לחיצה אחת:** שורת המצב מונה את התצוגות שכבר מוגדרות בנפרד,
וכפתור לצד כל אחת מחזיר אותה לעקוב אחרי הלוח המשותף.

נבדק: 20 בדיקות יחידה על המיזוג וההיקוף — כולל "אפשר להחזיר בנייד משהו שהלוח
מסתיר", "שכבה נמחקת כשחוזרים לערך של הלוח", ומעבר שלם דרך הדאטהבייס — ובדיקת
E2E שמוכיחה דרך הממשק עצמו שסגנון שנבחר למובייל לא נגע בטלוויזיה ולא במחשב.
