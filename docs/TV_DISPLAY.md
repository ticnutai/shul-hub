## הבעיה שהייתה צריכה פתרון: אפס סנכרון

לפני העבודה הזו לא היה בקוד **שום** מנוי `postgres_changes` — אפס. כל מסך קרא
את הנתונים פעם אחת, כשנטען. זה בסדר לנייד שנפתח ונסגר, אבל שגוי לחלוטין למסך
שנשאר על אותו דף במשך שבועות: גבאי שמשנה זמן תפילה לעולם לא היה מגיע לקיר.

### הפתרון — `src/community/lib/realtime.ts`

`useRealtimeSync()` נרשם לפיד השינויים של Postgres ומבקש מ-React Query לטעון
מחדש רק את הרשימה שהשתנתה.

שלוש שכבות הגנה, כי אין מי שילחץ "רענן":

1. **Realtime** — שינוי מגיע למסך תוך שנייה.
2. **טעינה תקופתית** — כל 5 דקות, ללא תלות בסוקט. אירוע שהוחמץ היה נשאר
   על המסך עד ריענון הדף, שעל קיר עלול לא לקרות לעולם.
3. **התחברות מחדש** — backoff מדורג עד 30 שניות, ואיפוס מיידי כשהרשת חוזרת
   (`online`). כל התחברות מחדש טוענת הכול, כי ייתכן שהוחמצו שינויים.

#### איך זה אומת

`scripts/verify-realtime.mjs` נרשם לשינויים, מבצע כתיבה, ומוודא שהאירוע
הגיע. הרצה חוזרת:

```bash
node scripts/verify-realtime.mjs
```

**למה כלי כזה נחוץ:** מנוי בלבד לא מוכיח דבר. Supabase Realtime מאשר
binding לכל שם טבלה — בדקתי עם בקרה, וגם `this_table_does_not_exist_xyz`
קיבלה "אישור". ניסיון קודם שהסתמך על סטטוס המנוי דיווח 8/8 הצלחה והיה
חסר ערך לחלוטין; הוא נמחק ולא נכנס לרפו.

הכתיבה היא no-op מכוון — אותו ערך נכתב בחזרה לאותה עמודה, כך שהנתונים
לא משתנים אבל Postgres עדיין מפיק UPDATE.

בנוסף אומת שהלוח עצמו מגיב: עם הלוח פתוח, כתיבה חיצונית גרמה לו לטעון
מחדש את `settings` לבד (2 → 3 בקשות), בלי ריענון דף ובלי נגיעה.

RLS לא מושפע: realtime מחיל את אותן מדיניות שורה, כך שמנוי מקבל בדיוק את
השורות שמותר לו לקרוא.

שלוש שקופיות מתחלפות אוטומטית, 20 שניות כל אחת:

1. **זמני תפילות** — מניינים של היום, עם סימון בולט של **המניין הבא**, לצד

הלוגיקה של חישוב הזמנים היא **בדיוק אותה לוגיקה** של האפליקציה
(`resolveDay`, `zmanimFor`) — לא שוכפלה, כדי שלא ייווצר הבדל בין המסך לנייד.

### הערה על `scripts/tv-cap.mjs`

ה-CLI של Capacitor מחפש `capacitor.config.ts` בשם קשיח ואין לו דגל `--config`
(נבדק ב-`@capacitor/cli/dist/config.js`). לכן הסקריפט מחליף את קובץ התצורה
לזמן הפקודה בלבד.

ההחלפה היא החלק המסוכן: אילו הייתה נשארת חצי-מיושמת, הבילד הבא של הנייד היה
יוצר APK עם ה-appId של הטלוויזיה בשקט. לכן השחזור רץ מתוך `finally` וגם
ממטפלי אותות, והמקור נשמר בזיכרון ולא בקובץ גיבוי שעלול להישאר ולהיראות

### ארבעה באגים שנמצאו רק על המכשיר — ותוקנו

2. **שיעורים לא לפי שעה:** 16:15, 08:45, 14:15, 15:15 (לפי `sort_order` של האתר).

## שליטה מלאה בלוח מהמחשב — `scripts/tv-control.mjs`

שני ערוצים, כי הם מגיעים לדברים שונים:

```
   המחשב                                    קופסת ה-TV
 ┌─────────────┐   ADB (adb shell)      ┌──────────────────────────────┐
 │             │ ─────────────────────► │ המכשיר: התקנה, הפעלה, מקשי   │
 │ tv-control  │                        │ שלט, צילום מסך, לוגים        │
 │   .mjs      │   CDP (DevTools)       │  ┌────────────────────────┐  │
 │             │ ─── adb forward ─────► │  │ בתוך ה-WebView: DOM,    │  │
 └─────────────┘   tcp:9222             │  │ JS, קונסול, רשת         │  │
                                        │  └────────────────────────┘  │
                                        └──────────────────────────────┘
```

`uiautomator` לא רואה שום דבר בתוך ה-WebView. זה נבדק על המכשיר ויצא ריק. לכן התוכן
נקרא דרך Chrome DevTools Protocol, כמו ש-`chrome://inspect` עושה.

```bash
npm run tv -- status            # מכשיר, אפליקציה, שקופית נוכחית, מצב סנכרון, אוטו-הפעלה
npm run tv -- text              # כל הטקסט שעל המסך
npm run tv -- eval "<js>"       # הרצת JavaScript בתוך הלוח
npm run tv -- console 30        # קונסול ושגיאות, 30 שניות
npm run tv -- network 30        # כל בקשות הרשת, 30 שניות
npm run tv -- shot tv.png       # צילום מסך מלא
npm run tv -- key down 3        # מקשי שלט: up/down/left/right/ok/back/home/menu
npm run tv -- reload | restart | install | autostart
```

**התחברות:** בטלוויזיה, הגדרות → אפשרויות מפתח → **ניפוי באגים אלחוטי**, ואז
`adb connect <ip>:<port>` עם הפורט שמוצג שם. **הפורט משתנה אחרי כל אתחול של הטלוויזיה.**

**אבטחה:** הערוץ לתוך ה-WebView (`webContentsDebuggingEnabled` ב-`capacitor.config.tv.ts`)
נגיש **רק** דרך חיבור ADB מאושר. Chromium מקבל חיבור רק מה-UID של ה-shell או של root.
מי שיש לו ADB יכול ממילא לשלוט במכשיר כולו, אז ההגדרה לא מרחיבה את הסיכון. **המתג האמיתי
לייצור הוא לכבות "ניפוי באגים אלחוטי" בטלוויזיה**, מה שסוגר את שני הערוצים. בנייה עם
`TV_WEBVIEW_DEBUG=0` משמיטה את הערוץ מה-APK.

**למה לא שרת MCP מוכן:** נבדקו mobile-mcp, android-mcp-server, scrcpy-mcp, mcp-adb ועוד.
כולם רואים רק את עץ הנגישות, **ואף אחד לא רואה בתוך WebView**. `chrome-devtools-mcp`
של Google יכול להתחבר ל-`localhost:9222` אחרי `adb forward`, אבל התמיכה שלו ב-WebView לא
מאומתת, ו-Puppeteer שעליו הוא בנוי נתקע מול אנדרואיד בחלק מהפקודות.

## הפעלה אוטומטית אחרי הפסקת חשמל

`BootReceiver.java` מפעיל את הלוח כשהטלוויזיה נדלקת.

מכשירי אנדרואיד TV לא עקביים לגבי איזה שידור אתחול הם שולחים, ולכן ה-receiver
מאזין לארבעה: `BOOT_COMPLETED`, `LOCKED_BOOT_COMPLETED`, `QUICKBOOT_POWERON`
ו-`com.htc...QUICKBOOT_POWERON`. כפילויות לא מזיקות — `MainActivity` היא
`singleTask`, כך ששידור שני מביא את המופע הקיים לחזית במקום ליצור עוד אחד.

> ⚠️ **זה best effort, ותלוי מכשיר.** אנדרואיד מגביל הפעלת activity מהרקע,
> וחלק מהמכשירים פשוט מסרבים. אם הלוח לא חוזר מעצמו — חפש בהגדרות הטלוויזיה
> אפשרות "הפעלה אוטומטית" / "Auto start" עבור האפליקציה. אי אפשר לעקוף את
> זה מהקוד. כישלון נתפס ונרשם ללוג במקום לקרוס, כדי שהמערכת לא תסמן את
> האפליקציה כבעייתית בכל אתחול.
