# ייצוא וייבוא נתונים — מדריך טכני

תיעוד זה מסביר איך בנוי פיצ'ר ייצוא/ייבוא הנתונים בפאנל הניהול (`/admin` → טאב "ייצוא/ייבוא"),
ואיך להרחיב אותו בעתיד.

## למה זה קיים

מאפשר לגבאי:

1. **לגבות** את כל תוכן האתר לקובץ אחד (Excel או JSON).
2. **לערוך בכמות** — למשל לפתוח את קובץ ה-Excel, לעדכן עשרות זמני מניינים בבת אחת, ולייבא בחזרה.
3. **להעביר תוכן** בין סביבות (פיתוח → ייצור) בלי לגעת ב-SQL.

## אילו טבלאות כלולות

מוגדר במערך `EXPORTABLE_TABLES` ב-`data-export.ts`, בסדר הזה (חשוב ל-import, ראו בהמשך):

1. `settings` — הגדרות כלליות של האתר (שם, כתובת, קואורדינטות, ערכת נושא)
2. `shiur_categories` — קטגוריות שיעורים
3. `minyanim` — מניינים וזמני תפילה
4. `announcements` — מודעות (מזל טוב / הודעות לציבור)
5. `shiurim` — שיעורים (מפנה ל-`shiur_categories` דרך `category_id`)
6. `chavrutot` — חברותות קיימות
7. `chavruta_requests` — בקשות לחברותא שהתקבלו מהציבור
8. `admin_messages` — הודעות שהתקבלו מהציבור לגבאי

### מה **לא** כלול, ולמה

| טבלה                                              | סיבה                                                                                                                                    |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `user_roles` (הרשאות admin/gabbai/user)           | ניהול הרשאות נעשה דרך טאב "משתמשים" הייעודי (RPC מאובטח). ייבוא עיוור של הרשאות הוא סיכון להעלאת הרשאות (privilege escalation).         |
| `notification_preferences`, `user_ui_preferences` | מידע אישי לכל משתמש (לא "תוכן אתר"), ומוגן ב-RLS כך שגבאי לא יכול לקרוא נתונים של משתמשים אחרים בכל מקרה (`user_id = auth.uid()` בלבד). |
| `migration_logs`                                  | יומן פנימי לסקריפט מיגרציות אד-הוק, לא תוכן שמנוהל ע"י גבאי.                                                                            |
| משתמשי `auth.users` עצמם                          | לא טבלה רגילה — נגישה רק דרך RPC (`admin_list_users` וכו'), לא דרך `select("*")`.                                                       |

## איך הייצוא עובד

1. `fetchAllData()` שולף `select("*")` מכל טבלה ב-`EXPORTABLE_TABLES`, דרך אותו לקוח Supabase
   שמשמש את שאר פאנל הניהול (`src/integrations/supabase/client.ts`) — כלומר עם ההרשאות של
   המשתמש המחובר, בכפוף למדיניות ה-RLS (`is_admin()`) שכבר קיימת על כל טבלה.
   **אין צורך במפתח service-role ואין קריאת שרת** — הכול קורה בדפדפן.
2. **JSON**: `downloadAsJson()` עוטף את הנתונים במעטפת קטנה —
   ```json
   {
     "exportedAt": "2026-08-20T12:00:00.000Z",
     "source": "shul-hub",
     "version": 1,
     "tables": { "minyanim": [...], "announcements": [...], ... }
   }
   ```
   ומוריד כ-Blob דרך `<a download>`.
3. **Excel**: `downloadAsExcel()` בונה חוברת עבודה עם ספריית [`exceljs`](https://www.npmjs.com/package/exceljs)
   — **גיליון אחד לכל טבלה**, שם הגיליון = שם הטבלה (עד 31 תווים, מגבלת Excel), שורה ראשונה = כותרות
   העמודות. ערכים שהם אובייקט/מערך (כמו `partners` ב-`chavrutot`) נשמרים כטקסט JSON בתא.

   > נבחרה `exceljs` ולא `xlsx`/SheetJS מה-npm registry, כי לגרסת ה-npm של `xlsx` יש שתי חולשות
   > אבטחה ידועות (Prototype Pollution, ReDoS) ללא תיקון זמין ב-npm.

## איך הייבוא עובד

1. המשתמש בוחר קובץ (`.json` / `.xlsx` / `.xlsm`).
2. `parseImportFile()` מזהה את הסוג לפי סיומת ומפעיל את הפענוח המתאים:
   - `parseJsonFile` — קורא את ה-JSON, מזהה גם מעטפת `{ tables: {...} }` וגם אובייקט שטוח של טבלאות.
   - `parseExcelFile` — קורא כל גיליון שהשם שלו תואם טבלה מ-`EXPORTABLE_TABLES`, הופך שורה ראשונה
     לשמות עמודות, ושאר השורות לרשומות.
3. מוצג **דיאלוג אישור** (`DataExportImportAdmin`) עם checkbox לכל טבלה וספירת רשומות שנמצאו בקובץ —
   כברירת מחדל מסומנות רק טבלאות שיש בהן רשומות. הגבאי יכול לבטל סימון לטבלאות שלא רוצים לגעת בהן.
4. בלחיצה על "אישור ייבוא", `importData()` מריץ **upsert** (`onConflict: "id"`) לכל טבלה נבחרת,
   **בסדר הקבוע** של `EXPORTABLE_TABLES` — כדי ש-`shiur_categories` תיכתב לפני `shiurim` שמצביע
   אליה דרך `category_id` (מפתח זר).
5. חוקי הייבוא:
   - **רק עדכון/הוספה, אין מחיקה.** אם מחקת שורה מהקובץ, היא לא תימחק באתר.
   - רשומה בלי `id` (או עם `id` ריק) **מדולגת** — הפיצ'ר הזה הוא merge/update, לא יצירת רשומות
     חדשות עם ID שנוצר ע"י השרת. כדי להוסיף רשומה חדשה דרך ייבוא, יש לתת לה `id` (UUID) בקובץ.
   - שגיאה בטבלה אחת לא עוצרת את הטבלאות האחרות — כל טבלה מדווחת הצלחה/כישלון בנפרד בדיאלוג.
6. בסיום, `queryClient.invalidateQueries()` מרענן את כל השאילתות בעמוד, כך שהנתונים המעודכנים
   מופיעים מיד בכל הטאבים בלי רענון ידני של הדפדפן.

## הרשאות ואבטחה

- כל הפעולות (שליפה וכתיבה) עוברות דרך ה-RLS הקיים במסד הנתונים: משתמש מחובר עם תפקיד
  `admin`/`gabbai` (נבדק ע"י פונקציית `is_admin()` ב-Postgres) יכול לקרוא ולכתוב לכל הטבלאות
  הרשומות ב-`EXPORTABLE_TABLES`. משתמש רגיל שינסה לגשת לטאב הזה יקבל שגיאת הרשאה מ-Supabase
  בפועל (הטאב עצמו גלוי רק לאחר מעבר ה-guard של `isAdmin` בעמוד `admin.tsx`).
- לא נוצר endpoint שרת חדש ולא נעשה שימוש במפתח service-role — כל הלוגיקה client-side, באותה
  רמת הרשאה שכבר יש לשאר פאנל הניהול.
- קובץ הייצוא (JSON/Excel) עלול להכיל מידע אישי (טלפון, אימייל מ-`chavruta_requests`,
  `admin_messages`) — יש להתייחס אליו כמסמך רגיש ולא להעלות אותו לשירותים חיצוניים לא מהימנים.

## הרחבה עתידית

- להוסיף טבלה חדשה לפיצ'ר: הוסף את שם הטבלה ל-`EXPORTABLE_TABLES` (במיקום הנכון מבחינת סדר
  מפתחות זרים) ותרגום עברי ל-`TABLE_LABELS`, ב-[`src/lib/data-export.ts`](../src/lib/data-export.ts).
  שאר הקוד (ייצוא, ייבוא, UI) גנרי לחלוטין ולא דורש שינוי.
- אם בעתיד יידרש ייצוא הכולל גם משתמשים/הרשאות, יש לבנות זאת דרך endpoint שרת ייעודי עם
  `client.server.ts` (מפתח service-role), כי `auth.users` לא נגיש דרך `select("*")` מהדפדפן —
  ראו הערה בראש `src/integrations/supabase/client.server.ts`.
